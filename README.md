# مخبز لالا (Lala's Bakery)

تطبيق طلبات ومتابعة وفروع + لوحات موظفين ومدير لمخبز لالا.  
واجهة أمامية: **Vite + React + TypeScript + Tailwind (RTL)** — خلفية وخدمات: **Supabase (Postgres + Auth + Realtime + Storage + RPC/RLS)** — استضافة: **Cloudflare Pages**.

> ملاحظة: هذا المستودع يعمل بدون مفتاح `service_role` في الواجهة/العميل. كل العمليات الحساسة تتم عبر RPCs بصلاحيات محددة وسياسات RLS.

---

## ما الذي يقدمه النظام

### للعملاء
- تصفح الفروع والمنتجات وإضافة للسلة وإتمام الطلب.
- طرق الاستلام: استلام من الفرع، توصيل داخل الفرع (لطاولة/مكان)، توصيل داخل نطاق العبور (حسب إتاحة الفرع).
- طرق الدفع: كاش / InstaPay (حسب إعدادات الفرع وحدود الكاش).
- صفحة متابعة الطلب برابط تتبع خاص (tracking key) + مشاركة/نسخ الرابط.

### للموظفين
- شاشة الطلبات الواردة مع تحديثات، تغيير الحالة، تأكيد/رفض الدفع، استلام الكاش، معالجة طلبات العبور.
- نقطة بيع (POS) داخل الفرع لإنشاء طلبات سريعة.

### للمدير
- إدارة الفروع/المنتجات/الإعدادات والتقارير.
- تحكم بإتاحة ورسوم وساعات ورسائل توصيل العبور لكل فرع.
- أداة تنظيف بيانات التجربة مع معاينة ونسخ احتياطي وسجل تدقيق غير قابل للحذف.

## الأجزاء المنفذة (Parts 1–7)

### الجزء 1 — التوصيل داخل الفرع (رقم الدور/المكان)
- **الحقول/المنطق:** اختيار رقم الدور مطلوب عند `delivery_type = table` مع مكان جلوس/غرفة اختياري (`delivery_spot`). قائمة أدوار افتراضية (5) قابلة للتعديل لكل فرع.
- **قاعدة البيانات:** `branches.delivery_floors` (قائمة أدوار)، `orders.delivery_floor`/`orders.delivery_spot` مع قيود تحقق.
- **التحقق:** تحقق على العميل وداخل RPC (`submit_order_v2` و `pos_create_order`)؛ الطلب لا يُنشأ بدون دور صالح للتوصيل داخل الفرع.
- **العرض:** يظهر الدور/المكان بشكل بارز للموظف والمدير وإيصال/تفاصيل الطلب (وللعميل نفسه عبر صفحة الطلب بمفتاح التتبع)، ولا يُعرَض عبر تتبع عام دون المفتاح.
- **الإدارة/POS:** تعديل الأدوار من لوحة إدارة الفروع؛ دعم إدخال الدور/المكان في POS.

### الجزء 2 — واجهة كروت الفروع (الشعار والغلاف)
- شارة شعار دائرية (خلفية بيضاء، إطار، ظل خفيف، `object-fit: contain`) متداخلة مع حافة الغلاف السفلية.
- غلاف بنسبة تقريبية 16:10 (حد أدنى للارتفاع على الموبايل) مع `object-fit: cover` وتدرج سفلي خفيف.
- نفس الأسلوب في الصفحة الرئيسية وصفحة الفرع مع الحفاظ على الاسم والوصف وروابط/أزرار المنيو والتواصل.

### الجزء 3 — إصلاحات POS ومنع حجب إنشاء الطلب
- السماح بطلبات POS كاش بدون رقم هاتف (الهاتف مطلوب فقط للطلبات الأونلاين الكاش حسب القواعد).
- اسم/هاتف العميل في POS اختياريان؛ قيود/منطق قاعدة البيانات و`pos_create_order` لا تمنع إنشاء طلب الفرع لأسباب خاصة بالأونلاين فقط (مثل بوابات أونلاين).
- رسائل خطأ عربية واضحة للموظف مع تسجيل التفاصيل التقنية في console للمساعدة في التشخيص.

### الجزء 4 — تنظيف بيانات التجربة والتقارير (للمدير فقط)
- شاشة/أداة "تنظيف بيانات التجربة" مع: اختيار نطاق تاريخ، خيارات (طلبات/عناصر/إثباتات دفع-ملفات/حركات مخزون/شيفتات وتقارير نقدية/إعادة إحصائيات العملاء عند الاختيار)، خيار "طلب تجريبي فقط" (`is_test`) إن وُجد.
- **معاينة قبل التنفيذ:** عرض الأعداد المتأثرة.
- **نسخ احتياطي:** تصدير CSV/JSON للبيانات المحددة قبل المسح.
- **تأكيد قوي:** كتابة كلمة **"حذف"** + إعادة إدخال كلمة مرور المدير (إعادة تحقق).
- **تنفيذ آمن:** RPCs بصلاحية مدير فقط (`SECURITY DEFINER`, `search_path` ثابت، داخل معاملة واحدة) لحذف البيانات المحددة وإرجاع المخزون المحجوز عند الحاجة.
- **سجل تدقيق غير قابل للحذف:** `data_wipe_audit` يسجل (من/متى/النطاق/الخيارات/الأعداد) بدون صلاحيات تعديل/حذف لأدوار التطبيق.
- **حماية:** لا يلمس المنتجات أو الفروع أو الأسعار أو الإعدادات أو حسابات الموظفين أو سجلات موافقة العملاء إلا إذا حُدد ذلك صراحةً.
- **التقارير:** استبعاد الطلبات/الشيفتات المعلّمة `is_test=true` من تقارير المدير.

### الجزء 5 — تحكم المدير في توصيل العبور (لكل فرع)
- إعدادات لكل فرع: تفعيل/إيقاف، رسوم (افتراضي 50)، ساعات عمل اختيارية، رقم واتساب، قالب رسالة واتساب، رسالة عدم التوفر/الإغلاق.
- **فرض على الخادم:** `submit_order_v2` يرفض طلبات العبور عند عدم الإتاحة ويستخدم الرسوم/الإعدادات الفعلية للفرع (ليس اعتمادًا على الواجهة فقط).
- **واجهة العميل:** يظهر خيار العبور كغير متاح/معطّل مع رسالة الفرع عند الإغلاق؛ تحديثات فورية (Realtime/استطلاع قصير) عند تغيير المدير.
- **صلاحيات وتدقيق:** مدير فقط عبر RPC (`manager_set_obour_settings`) مع سجل `obour_settings_audit` وRLS.

### الجزء 6 — العنوان وتأكيد اللوكيشن لطلبات العبور
- **حقول مطلوبة (عبور):** الاسم، رقم موبايل مصري صحيح، عنوان تفصيلي، وعلامة مميزة اختيارية — مع تحقق عميل وخادم.
- **بعد إنشاء الطلب:** تظهر خطوة "ابعت لوكيشنك على واتساب" برقم الطلب (عرض رقم واتساب الفرع + نسخ + فتح `wa.me` برسالة جاهزة من القالب `{order_number,name,address}`) مع خانة تأكيد إلزامية.
- **تأكيد اللوكيشن:** يتم تسجيل `location_confirmed` و`location_confirmed_at` عبر RPC مرتبط بمفتاح التتبع (`confirm_obour_location`) أو تأكيد موظف الفرع (`staff_mark_location_received`).
- **منع التحضير قبل التأكيد:** قاعدة البيانات تمنع نقل طلب العبور الأونلاين إلى "جاري التحضير" ما لم يُؤكَّد اللوكيشن.
- **تنبيهات/انتهاء:** تذكير افتراضي (20 دقيقة) ورسالة انتظار، وإلغاء تلقائي مع إرجاع المخزون للطلبات غير المؤكدة بعد مهلة (افتراضي 45 دقيقة) عبر `expire_unconfirmed_obour_orders` (مع محاولة جدولة pg_cron إن توفرت).
- **خصوصية:** العنوان/الهاتف/تفاصيل اللوكيشن متاحة للموظف والمدير وللعميل نفسه عبر صفحة الطلب بمفتاح التتبع، ولا تُعرَض في تتبع عام بدون المفتاح.

### الجزء 7 — ملاحظات على الطلب قبل الدفع
- حقل اختياري "ملاحظات على الطلب" (حد أقصى 300 حرف) مع عداد حي ونموذج placeholder.
- **تخزين آمن:** `orders.customer_note` مع تقليم/فحص الطول على الخادم (ورفض >300).
- **العرض:** تظهر بشكل بارز للموظف وPOS والإيصال/ملخص الطلب (وللعميل نفسه في ملخص الطلب بمفتاح التتبع)، ولا تُعرَض كـ HTML.

## الترقيات (Migrations) والخطوات اليدوية على Supabase

> نفّذ الترقية على مشروع Supabase الصحيح وبالترتيب. لا تستخدم `service_role` في التطبيق.

**الترتيب (Parts 1–7):**
1. `0028_part1_delivery_floor_spot.sql`
2. `0029_part3_pos_fix.sql`
3. `0030_part4_test_data_wipe.sql`
4. `0031_part4_reports_exclude_test.sql`
5. `0032_part5_obour_controls.sql`
6. `0033_part6_obour_location.sql`
7. `0034_part6_obour_submit_and_details.sql`
8. `0035_part7_customer_note.sql`

**بعد التنفيذ:**
- أعد تحميل مخطط PostgREST: `select pg_notify('pgrst','reload schema');`
- تحقّق من وجود/جدولة مهمة انتهاء طلبات العبور غير المؤكدة (`expire-unconfirmed-obour-orders`, كل 5 دقائق) إذا كان `pg_cron` مفعّلًا؛ وإن لم يكن متاحًا فجدولها يدويًا حسب بيئة Supabase.

**ملاحظات تشغيلية:**
- تأكد من إعدادات Turnstile/المفاتيح العامة في البيئة (`VITE_*`) ومن صلاحيات Storage لإثباتات الدفع حسب سياسات المشروع.
- ملفات إثباتات الدفع المحذوفة ضمن "تنظيف بيانات التجربة" تُزال مراجعها في قاعدة البيانات ضمن المعاملة؛ إزالة ملفات Storage تتم من جهة العميل بجلسة مدير (best-effort) بعد إرجاع المسارات.

## الأمان والصلاحيات (ملخص)

- تفعيل RLS على الجداول/الوظائف الحساسة؛ فصل صلاحيات الموظف (فرعه) والمدير (جميع الفروع) ومنع وصول anon للطلبات.
- دوال `SECURITY DEFINER` مع `search_path` ثابت وفحوصات دور/فرع وتحقق من المدخلات.
- بيانات حساسة (عنوان/هاتف/لوكيشن العبور، ملاحظات، دور/مكان التوصيل داخل الفرع) لا تُكشف في تتبع عام؛ الوصول المسموح عبر مفتاح تتبع العميل نفسه أو صلاحيات الموظف/المدير.
- سجلات تدقيق غير قابلة للحذف: `data_wipe_audit`, `obour_settings_audit`.
- راجع: `tests/security/SECURITY_CHECKLIST.md` و `tests/security/parts4to7-checks.mjs` و `tests/security/run-security-checks.mjs`.

## الاختبارات والتحقق

- **تحقق ثابت/بناء:** `npx tsc --noEmit` ثم `npm run build` (يتضمن فحص التباين وvite build).
- **اختبارات أمان (تتطلب بيئة/بيانات اعتماد):**
  - `node tests/security/run-security-checks.mjs`
  - `node tests/security/cash-payment-checks.mjs`
  - `node tests/security/parts4to7-checks.mjs`
  (تحتاج متغيرات مثل `SUPABASE_URL`, `SUPABASE_ANON_KEY` ومعرّفات فروع/منتجات/طلبات واعتمادات موظف/مدير حسب السيناريو.)
- **E2E (Playwright):** `npm run test:e2e` (يتطلب تشغيل المعاينة/الخادم المناسب، راجع `playwright.config.ts`).
- **تحقق يدوي موصى به بعد النشر:**
  - POS: كاش بدون هاتف، InstaPay، توصيل داخل الفرع مع دور/مكان، عرض الملاحظات.
  - عبور: إيقاف/تفعيل من المدير ينعكس فورًا، رفض بدون عنوان/هاتف، خطوة تأكيد اللوكيشن، منع "جاري التحضير" قبل التأكيد، التذكير/الإلغاء التلقائي.
  - تنظيف بيانات التجربة: معاينة، تصدير، تأكيد "حذف"+كلمة مرور، تنفيذ، وسجل تدقيق.
  - أحجام شاشات 360/390/430px ولقطات قبل/بعد (390px) للشاشات المتغيرة.

## هيكل المشروع (مختصر)

- `src/pages/*` — صفحات العميل/الموظف/الإدارة (Checkout, Order, StaffOrders, StaffPOS, BranchesAdmin, ReportsAdmin, Home, BranchLanding…)
- `src/lib/*` — أنواع، تنسيق، تكامل Supabase وأدوات مساعدة
- `supabase/migrations/*` — ترقيات قاعدة البيانات (نفّذها بالترتيب)
- `tests/security/*` — فحوصات أمان/منطق وChecklist
- `tests/e2e/*` — اختبارات Playwright

## التشغيل محليًا (تطوير)

```bash
npm install
npm run dev
```
